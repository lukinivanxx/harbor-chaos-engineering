# CHAOS_RESEARCH — исследование сценариев отказа

Документ описывает выбранные chaos-сценарии, реальные причины таких
отказов и меры защиты. Все сценарии реализованы через fault injection
в Istio (service mesh), что позволяет вносить ошибки в сетевой трафик
без изменения кода приложения.

## Общий подход

Istio внедряет sidecar-прокси (Envoy) рядом с каждым компонентом Harbor.
Весь сетевой трафик проходит через эти прокси, что даёт возможность
управлять им: вносить задержки и возвращать ошибки. Это основа
Chaos Engineering — проверки устойчивости системы к сбоям в
контролируемых условиях, до того как сбой случится в реальности.

Выбраны 3 сценария из разных категорий задания.

---

## Сценарий 1: Задержка между пользователем и приложением

**Что делаем:** вносим задержку 5 секунд на входящий HTTP-трафик через
Istio Ingress Gateway (путь пользователь → приложение).

**Реализация:** VirtualService с `fault.delay`, привязанный к Gateway.

### Примеры из реальных условий

- Перегрузка сети между клиентом и дата-центром (например, пиковый
  трафик, DDoS, проблемы у интернет-провайдера).
- Медленный ответ балансировщика нагрузки или reverse-proxy под высокой
  нагрузкой.
- Географическая удалённость клиента.

### Меры защиты

- **Таймауты на стороне клиента и шлюза**
- При росте задержек временно
  прекращать слать запросы к перегруженному сервису, давая ему
  восстановиться.
- **Автомасштабирование** входного шлюза по нагрузке.

---

## Сценарий 2: Ошибка HTTP 500 между компонентами приложения

**Что делаем:** возвращаем HTTP 500 вместо ответа компонента portal
(веб-интерфейс Harbor) для трафика через Istio Gateway.

**Реализация:** VirtualService с `fault.abort` (httpStatus 500).

### Примеры из реальных условий

- Необработанное исключение в коде компонента (баг, приводящий к 500).
- Компонент не может подключиться к своей зависимости (БД, кэш) и
  отвечает ошибкой.
- Исчерпание ресурсов (память, файловые дескрипторы) — компонент падает
  при обработке запроса.

### Меры защиты

- **Graceful degradation** — при отказе некритичного компонента (например,
  portal) остальная система (registry, API) продолжает работать.
- **Тестирование** (CI/CD с автотестами), canary-деплой —
  выкатывать новую версию постепенно.

## Сценарий 3: Задержка между registry и остальными компонентами

**Что делаем:** вносим задержку 5 секунд на трафик к компоненту registry
(хранилище образов). Проверяется изнутри mesh, так как registry —
внутренний сервис.

**Реализация:** VirtualService с `fault.delay`, нацеленный на сервис
harbor-registry.

### Примеры из реальных условий

- Медленное хранилище (registry работает с диском/объектным хранилищем;
  деградация storage backend замедляет ответы).
- Перегрузка registry при массовом push/pull образов (например, CI
  одновременно тянет образы на десятки нод).
- Сетевые проблемы между компонентами внутри кластера.
- Нехватка ресурсов у пода registry (CPU throttling, недостаток памяти).

### Меры защиты

- **Кэширование образов** (pull-through cache, локальные зеркала), чтобы
  снизить нагрузку на registry.
- **Горизонтальное масштабирование** registry (несколько реплик) —
  в проде, в отличие от тестового окружения с 1 репликой.
- registry с алертами на рост времени ответа.

## Выводы

Проведённые эксперименты показывают, что fault injection в Istio —
эффективный способ проверить устойчивость системы без изменения кода
приложения. Ключевой урок: отказ одного компонента не должен приводить
к отказу всей системы. Основные защитные механизмы — таймауты,
health checks, graceful degradation и мониторинг.

Важное техническое наблюдение: Istio fault injection работает только для
HTTP/gRPC-трафика. Для протоколов на чистом TCP (например, PostgreSQL
между Harbor и его базой данных) требуется другой инструмент — например,
Chaos Mesh с NetworkChaos, вносящий задержку на сетевом уровне через
tc/netem. Это ограничение важно учитывать при планировании chaos-тестов.

# Harbor Chaos Engineering на k3s + Istio

Автоматизированное развёртывание однонодового Kubernetes (k3s) с приложением
Harbor и проведение Chaos Engineering экспериментов с помощью Istio.

## Что делает решение

1. Устанавливает k3s (однонодовый Kubernetes) без traefik
2. Устанавливает Istio (service mesh, профиль demo)
3. Разворачивает Harbor (registry, версия 2.14.0) через Helm
4. Настраивает Istio Ingress Gateway как точку входа
5. Предоставляет 3 chaos-сценария из разных категорий

## Требования

- ОС: Ubuntu 22.04 amd64
- Пользователь в группе sudo
- Минимум 6 GB RAM, 4 CPU, 40 GB диска
- Доступ в интернет (для скачивания k3s, Istio, Harbor)

## Установка

Одна команда разворачивает всё с нуля:

```bash
cd harbor-chaos
./setup.sh
```

Установка занимает 5-10 минут. Скрипт идемпотентен — можно
запускать повторно без вреда.

По завершении скрипт выведет адреса доступа к Harbor и данные для входа
(admin / Harbor12345).

## Проверка установки

После `setup.sh` убедитесь, что всё работает:

```bash
# Все поды должны быть в статусе Running (READY 2/2 или 3/3)
kubectl get pods -n harbor

# Harbor отвечает healthy по всем компонентам
curl http://<IP-ноды>:30002/api/v2.0/health
```

IP ноды скрипт выводит в конце установки. Внутри ВМ обычно 10.0.2.15.

## Запуск chaos-сценариев

Каждый сценарий проходит по одной схеме:
демонстрация работы → пауза → внедрение ошибки → демонстрация
последствий → пауза → откат к норме.

### Сценарий 1: Задержка между пользователем и приложением

```bash
cd chaos
./scenario-01-delay.sh
```

Вносит задержку 5 секунд на входящий трафик через Istio Gateway.
Категория: задержка HTTP-ответа между пользователем и приложением.

### Сценарий 2: Ошибка 500 между компонентами

```bash
./scenario-02-abort.sh
```

Вносит HTTP 500 на трафик к компоненту portal через Istio Gateway.
Категория: status code 500 между компонентами приложения.

### Сценарий 3: Задержка между registry и остальными

```bash
./scenario-03-delay-registry.sh
```

Вносит задержку 5 секунд на трафик к компоненту registry.
Проверяется изнутри mesh (registry — внутренний компонент).
Категория: задержка для harbor между registry и остальными компонентами.

## Что увидит проверяющий

Для каждого сценария на паузах можно вручную убедиться в эффекте:

- Сценарий 1: время ответа вырастает с ~0.01с до ~5с, затем возвращается
- Сценарий 2: HTTP-код меняется с 200 на 500 (тело ответа: fault filter
  abort — подпись Istio), затем возвращается на 200
- Сценарий 3: время ответа registry вырастает с ~0.02с до ~5с, затем
  возвращается

## Технические детали

- Kubernetes: k3s (traefik отключён, чтобы не конфликтовать с Istio)
- Service mesh: Istio, профиль demo
- Приложение: Harbor 2.14.0 (chart 1.18.0), по 1 реплике каждого компонента
- Доступ: NodePort 30002 (напрямую) и Istio Ingress Gateway (для сценариев)

## Очистка

Полное удаление всего окружения:

```bash
helm uninstall harbor -n harbor
kubectl delete namespace harbor
istioctl uninstall --purge -y
/usr/local/bin/k3s-uninstall.sh
```
